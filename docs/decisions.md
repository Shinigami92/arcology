# Decisions

Short log of architectural decisions and why. Newest at the bottom. Supersede an entry by adding a new one that references it; don't rewrite history.

Format: `## D-NNN: Title (YYYY-MM-DD)`, then 2–5 lines: decision, why, consequences.

## D-001: Godot 4.7, Forward+, D3D12 (2026-09-27)

Godot 4.7.2 stable, Forward+ renderer, D3D12 driver on Windows. The 4.7.2 binary ships `XR_KHR_D3D12_enable`, so OpenXR works on D3D12. If SteamVR shows problems on D3D12 (black eyes, crashes, missing depth submission), switch `rendering/rendering_device/driver.windows` to `vulkan` and log it here.

## D-002: Godot MCP: godot-ai (2026-09-27)

[godot-ai](https://github.com/hi-godot/godot-ai), pinned in `.mcp.json` (`godot-ai==4.2.3`), editor plugin in `addons/godot_ai/`. Chosen in Milestone 0 over GDAI MCP and IvanMurzak's Godot-MCP: open source, captures the editor viewport, a scene camera and the running game's framebuffer, reads game/editor logs, and evaluates GDScript in the running game (used by the perf test). The `_mcp_game_helper` autoload must stay enabled for game capture and eval.

## D-003: Blender MCP: Blender Lab MCP server (2026-09-27)

The official [Blender Lab MCP server](https://www.blender.org/lab/mcp-server/), path supplied via `BLENDER_MCP_PATH` so the repo stays machine-independent.

## D-004: Godot XR Tools 4.6.0-dev1 (2026-09-27)

XR Tools 4.5.1 (latest stable) fails to parse on Godot 4.7 (`viewport_2d_in_3d.gd`: "Not all code paths return a value"). 4.6.0-dev1 fixes the 4.7 return-value issues and ran clean in the official demo on the Steam Frame. Installed into `addons/godot-xr-tools/` unmodified (its `plugin.cfg` still says 4.5.1; `VERSIONS.md` has the 4.6.0 notes). Switch to 4.6.0 stable when it ships. Don't patch the addon; wrap or extend it in `core/` instead.

## D-005: Jolt, 90 Hz physics, no V-Sync (2026-09-27)

Jolt physics, `physics_ticks_per_second=90` to match the display, so held objects and hands move in lockstep with frames and physics interpolation isn't needed. V-Sync off: the OpenXR runtime paces frames, and V-Sync on the desktop mirror window would add latency. If the headset runs at 120 Hz later, raise the tick rate to match (or enable physics interpolation) and re-run the perf test.

## D-006: MSAA 4x, depth submission (2026-09-27)

Start with MSAA 4x (3D), no TAA/FSR (smearing and ghosting are worse in VR). `xr/openxr/submit_depth_buffer=true` so SteamVR can use depth for reprojection. Both are to be validated against the budget in the first perf run.

## D-007: Git LFS for all binaries, including addons (2026-09-27)

`.gitattributes` routes 3D, image, audio, video, font and binary Godot resources (`.res`, `.scn`) to LFS everywhere, addons included, so binaries never land in normal Git history. Text resources (`.tscn`, `.tres`, `.gdshader`, `.gltf`) stay in Git and are diffable. Prefer text formats for everything we author.

## D-008: World scale and coordinates (2026-09-27)

1 unit = 1 m, Y up, glTF/Godot conventions (-Z forward). The apartment floor is at y = 0 and is the world origin, to keep float precision best where the player spends the most time. The apartment sits 180 m above street level, so the street plane is y = -180. The apartment's main window faces -Z ("north" by convention). Every zone is authored in world coordinates at its real position; the zone loader never offsets zones. Distant layers seen from the window must use the same frame so they line up with zones built later.

## D-009: Locomotion defaults: smooth move and smooth turn, seated-first (2026-09-27)

The user plays mostly seated and isn't prone to motion sickness. Defaults: smooth (direct) movement and smooth turning, no teleport. Teleport, snap turn and the comfort vignette are available as options. Stick-click sprint felt tedious, so sprint is automatic past a stick-deflection threshold. Design for seated play: eye-height calibration to a standing adult, a recenter action, and no interactable that requires reaching the floor.

## D-010: VoxelGI first for lighting (2026-09-27)

The apartment needs a live day/night cycle, so sun-dependent lighting can't be baked into static lightmaps. Start with one VoxelGI per zone (baked geometry, real-time light updates), with ReflectionProbes for glossy surfaces. Measure its GPU cost in the first perf run; if it blows the budget, fall back to LightmapGI for sun-independent interior lights plus real-time sun and sky light.

## D-011: Vulkan instead of D3D12 (2026-09-27, supersedes D-001's driver choice)

With SteamVR running, D3D12 logged `_texture_create_shared_from_slice: owner_info.allocation` errors every frame (creating texture slices from the OpenXR swapchain) and the captured XR frame was black. Vulkan starts the same session cleanly. Vulkan is Godot's most-tested OpenXR path, so the driver is Vulkan (the project default, so `project.godot` has no explicit driver line). Retry D3D12 after a Godot update if there's a reason to.

## D-012: VoxelGI rejected for stereo; no GI in M1 (2026-09-27, supersedes D-010)

Measured in the apartment flythrough at the real per-eye target (2 × 2644²): baked VoxelGI (subdiv 64, half-resolution GI) raises GPU p95 from 5.8 ms to 11.6 ms, more than the whole frame. The node and its baked data stay in the apartment scene, hidden, so the cost can be re-measured later. M1 lights with direct lights, sky ambient and one ReflectionProbe. For M2's day/night cycle, measure these in order: LightmapGI for sun-independent interior bounce plus real-time sun and sky; SDFGI at the lowest settings; a scripted fill light driven by world state.

## D-013: Perf test runs in XR or as a desktop approximation (2026-09-27)

`tools/perf` runs the zone's PerfPath either in the headset (real stereo, paced by SteamVR) or with `--xr-mode off`, rendering a 5288×2644 SubViewport (both eyes side by side at SteamVR's 100% render target for the Steam Frame). Desktop mode checks only GPU/CPU cost and scene counts, not frame pacing. It isn't multiview, so it overestimates culling/CPU cost slightly and matches per-pixel cost well. Claude runs desktop mode on every perf-relevant change; the user runs XR mode before a milestone is called done.

## D-014: No OpenXR depth submission while MSAA is on (2026-09-27, supersedes D-006's depth part)

With `submit_depth_buffer` and MSAA 4x together, every XR frame logged `Image needs the TEXTURE_USAGE_STORAGE_BIT usage flag` (the MSAA depth resolve is a compute pass that can't write into SteamVR's depth swapchain). That was about 64k error chains in a 12-minute session, which also flooded the editor's debugger. Either setting alone is clean. MSAA 4x matters more for edge quality in VR than depth-assisted reprojection, so depth submission is off. Revisit if a Godot update fixes the resolve path.

## D-015: Generated blockout apartment (2026-09-27)

The apartment grew to five rooms (bedroom, living room, kitchen, hallway, bathroom) plus a vestibule behind the entrance, after the first headset test ("one room feels a bit small"). The blockout scene is generated by `tools/blockout/apartment.py` from a compact layout (walls as lines with door/window openings). This makes layout iterations cheap and diffs readable. Hand edits to `zones/apartment/apartment.tscn` get overwritten. Blender geometry replaces the blockout room by room later, at which point the generator stops owning those parts. The VoxelGI node and its baked data were dropped with the old layout (D-012).

## D-016: Seated reach: handles at 1.1 m, visible ranged grab, seats (2026-09-27)

In the first headset test the door handle at 1.0 m was too low to reach seated, and picking things up from low surfaces was hard. Handles go to 1.1 m. XR Tools' ranged grab (point, then grip, and the object flies to the hand) was already on but invisible, so each hand now draws a ray and highlights the target (`GrabRay`, `GrabHighlight`). Seats (sofa, bed edge) let the player sit down with X: the view moves to a seated eye point, and X or the move stick gets them up. Doors can't swing through the player anymore (`HingeBodyBlocker`); they used to, which let the player end up inside a door and walk through it.

## D-017: Own ranged grab; XR Tools' is broken in 4.6.0-dev1 (2026-09-27)

`function_pickup.gd` rejects every ranged target: it checks `target.has_method('can_ranged_grab')`, but `can_ranged_grab` is a property. 4.5.1 had `'can_ranged_grab' in target`, and master still has the regression. Instead of patching the addon, `GrabRay` does the targeting (cone up to 6 m, 12°, line of sight against static world), highlights the target, and on grip hands it to the pickup's `_pick_up_object()`, the same call XR Tools' own ranged grab makes. XR Tools' `ranged_enable` is off on both hands. Drop `GrabRay`'s targeting once upstream is fixed, or keep it for the line-of-sight check.

## D-018: Doors move their physics body explicitly (2026-09-27)

An `AnimatableBody3D` under a rotating hinge kept its old physics transform: the door looked open while its collision stayed shut (an invisible wall), and doors that had to be pushed couldn't open because the hand hit the still-closed collision. Door bodies are now `KinematicFollower`s: `top_level`, copying the leaf's transform onto themselves every physics frame, which is how `AnimatableBody3D` expects to be moved. Verified with capsule sweeps through all four doorways, closed and open. Any future moving interactable with collision (drawers, lids, fridge doors) uses the same pattern.

## D-019: Steam Frame controller profile and named actions (2026-09-27)

Without a binding for the Frame controller (`/interaction_profiles/valve/frame_controller_valve`, extension `XR_VALVE_frame_controller_interaction`, supported by Godot 4.7), SteamVR emulated a Touch controller: A/B/X/Y all sit on the Frame's right controller, and Touch's left X/Y landed on the left D-pad. The action map now has a Frame profile, and gameplay uses named actions (`jump`, `crouch`, `interact`, `recenter`) bound per controller: Frame right A/B/X/Y, Touch right A/B + left X/Y, Index right A/B + left A/B. Add new gameplay buttons as named actions, never as raw `ax_button`/`by_button`.

## D-020: Skyline window anti-aliasing tuned by measurement (2026-09-27)

The first AA attempt (1 px edge smoothing, fade to average at 0.35–0.9 cells per pixel) shimmered more than no AA at all. Measured as the share of city pixels changing by more than 0.1 luminance under a half-pixel head rotation: no AA 8.9%, first attempt 12.4%. Now: 2 px edge smoothing, fade at 0.2–0.5 cells per pixel, far average at 50% brightness (the tonemapper compresses bright windows, so the true average reads too bright): 5.5%, keeping mid-distance windows. Softer settings go down to 1.7% but turn most towers into flat slabs. The real fix is M2's prefiltered, mipmapped panorama and impostor layers.

## D-021: Holding a handle lets that hand pass through its own door (2026-09-28)

Doors that open away from the player couldn't be pushed open: the collision hand collides with static geometry, the door leaf is static geometry, so pressing the handle forward stopped the hand at the leaf, and the hinge never turned. Pulling worked only because the hand moved away from the leaf. `GrabPassThrough` adds a collision exception between the holding hand and the door body while a handle is held. Two XR Tools 4.6 quirks: `grabbed` fires twice per grab and Jolt counts exceptions, so the exception is only added once per hand; and `released` never fires, so removal listens to `dropped`. Every hinged or sliding interactable with a handle needs this.

## D-022: Jump tucks the body; the player body ignores pickables (2026-09-28)

Under the 2.6 m ceiling a 1.8 m body can lift its feet only 0.8 m, too little to land on a 0.75 m table. While airborne after a jump the body shrinks to 1.1 m (tucked feet), and on landing it regrows upward: the origin rises by the height regained each frame, because XR Tools regrows downward and would push the feet into whatever was landed on. The player also has air control (`ground_control = ALWAYS`) and a 4.3 m/s jump. The player body no longer collides with pickables (mask without layer 3): landing on a 50 g can launched the player at 37 m/s. Hands still push and grab them. Surfaces the player can stand on get solid collision volumes (the generator's per-box collision override), never thin plates.

## D-023: Interaction and shimmer tests (2026-09-28)

`tools/tests/` holds runnable suites started through `main.gd` (`-- --test=<suite>`), so the XR Tools autoloads exist, unlike with `--script`: `interaction` (doorways closed/open against the physics server, door blocker, grab pass-through, jump height and table landing, eye height after landing, ranged grab pull and line of sight) and `skyline` (shimmer under a half-pixel head turn). Run `interaction` after any change to the player, props or the apartment generator. They don't need the editor or the headset. Measured with `skyline`: the window glass and glow don't cause the remaining flicker (5.3% through glass, 6.7% without, 5.4% without glow). What the headset still shows is likely residual aliasing plus the Steam Frame's video stream, where tiny bright dots are a worst case for compression. Deferred to the Blender/panorama rebuild.

## D-024: XR perf counts dropped frames, not frames over 11.1 ms (2026-09-28)

The first in-headset run "failed" with 51% of frames over 11.1 ms while the GPU p95 was 4.5 ms and CPU p95 1.7 ms. In XR the runtime paces frames to 90 Hz, so frame intervals jitter around 11.11 ms (average 11.24 ms) and half of the normal frames land a hair above. A real drop is a missed refresh (about 22 ms). The frame budget is now `frames_dropped_pct`: intervals over 1.5x the budget (16.7 ms), at most 0.5%. `frames_over_budget_pct` and `frame_ms_p99` stay in the report for reference.

## D-025: M1 hitches come from the machine, not shader compiles (2026-09-28)

The perf report now counts pipeline compilations per frame (`pipeline_compiles`, `pipeline_compiles_at`, and per dropped frame). The apartment compiles 14 pipelines during warmup and 1 later (a 5 ms frame, no hitch); none of the dropped frames compile anything, and their GPU and CPU times are normal (4–6 ms, 1–2 ms). An almost empty Godot project hitches the same way, about 50 ms every 5 s plus one every 10 s, on Vulkan, D3D12 and OpenGL, but not headless: something on the PC stalls the GPU or present. Prime suspect: Prometheus scrapes `nvidia_gpu_exporter` (NVML queries) every 5 s; also running: GPU Tweak III, RTSS, PresentMon, windows_exporter, Wallpaper Engine. `tools/perf/stall_probe.tscn` measures the machine alone; run it before trusting `frames_dropped` in a perf report. No shader precompile helper for now; revisit when a report shows compiles on dropped frames.

## D-026: Blender assets: scripted builds, two glbs per hinged prop (2026-09-28)

Assets are built by Blender Python scripts run in background mode from Bash (`blender/<category>/<name>/*.py`, next to the `.blend`), so they're reproducible and several artists can work in parallel without sharing one Blender session. A hinged prop ships as two glb files (body with `-convcolonly` boxes; door with its origin on the hinge axis and a `HandleGrip` empty), so the Godot scene can put the door under an XR Tools hinge without restructuring an imported scene. Textures are baked PBR embedded in the glb; Godot extracts them next to the glb on import (VRAM-compressed, mipmapped), and those PNGs and `.import` files are committed. `blender/.gdignore` keeps Godot from importing `.blend` files itself (it unpacked textures into `blender/` and failed). First case: the fridge, built twice from one brief (Fable 5.1 and Opus 5.5, both `high`) for a blind headset comparison. Both were good enough to keep; Fable's won by a small margin, mostly for its door interior (Fable 31 min, 5.5 k triangles; Opus 26 min, 10.6 k triangles, more interior detail). The winner's scripts live in `blender/props/fridge/`.

## D-027: Hinges keep their momentum (2026-09-28)

XR Tools hinges stop dead when released, which felt wrong in the headset ("give the door a realistic swing"). `HingeSwing` estimates the hand's angular speed over the last 0.12 s before release, then keeps the hinge moving with constant friction plus damping, bounces off the open limit, and stops where the body blocker holds the leaf. A latch zone near closed pulls it shut: 15° for the fridge's magnetic seal, 3° for the apartment doors' catch. It replaces the fridge-only latch. Tuned by feel so a firm push swings the fridge door about 45° further and a flick shuts it; the doors swing longer (less friction). Confirmed in the headset: "much better now".

## D-028: Shared Blender toolkit (2026-09-28)

About 60% of the fridge's build scripts had nothing to do with fridges: bmesh primitives, bevel/boolean/shading, a shader-node builder, the bake into albedo/normal/ORM with the glTF occlusion setup, the export settings (triangulate for tangents), the studio render and the clearance checks. They moved to `blender/lib/arcology_blender/`, plus reusable wear layers (edge highlights, smudges, scuffs, dust, grime) and generic material recipes (white and dark plastic, frosted plastic, rubber, paint, paper). An asset's scripts keep only its dimensions, shapes and specific looks. Why: every asset gets the same material quality and bake settings, which matters for a coherent realistic look; artists spend their time on the asset, not on rebuilding the pipeline; fixed pipeline bugs stay fixed; and A/B runs compare models on the asset. Part tags moved from `fridge_part` to `arcology_part`. `ARCOLOGY_OUT_DIR` redirects a stage's outputs, so an asset can be rebuilt and compared with the committed files without overwriting them.

## D-029: Sofa A/B: Opus's sofa in the apartment, Fable's kept as a variant (2026-09-28)

Second blind A/B, both artists on the shared toolkit (D-028). Both were good enough to keep again; Opus 5.5's petrol-teal sofa won by a small margin for its texture realism (piping on every seam, creases, rub, pilling, stains; 25 min, 202 k tokens, 32 k triangles with pillow), against Fable 5.1's grey-blue boucle (18 min, 151 k tokens, 14 k triangles). Score so far: 1–1. The runner-up isn't discarded: it becomes `assets/props/sofa/sofa_boucle.tscn` for later apartments, so they don't all look the same. The winner's generic helpers were promoted into the library (`soft`: upholstered blocks, dents, lumps, throw pillows with a seam attribute; `fabric`: weave, welts, creases, rub, pilling, stains; `geo.join`, `geo.remove_attribute`, `Graph.attribute`, `Graph.dist_xy`), checked by rebuilding the sofa into a scratch folder with byte-identical glbs. The boucle sofa keeps its own helpers in `blender/props/sofa_boucle/helpers.py`. During an A/B, artists must not change `blender/lib/`; new generic code goes into their own `lib_candidates.py`.

## D-030: Blind A/B in place, and drawers that slide on (2026-09-29)

Two beds and two wardrobes don't fit side by side, so A/B variants now share one spot: an `ABSwitch` (`core/debug/`) holds children `A` and `B` and shows one; the hidden one is also disabled, so its collision leaves the physics world (tested). A physical `ABPanel` on the wall (a hand-pressed XR Tools area button with an "A / B" label) flips every switch at once. The apartment generator writes pairs from `AB_INSTANCES`. Drawers are `XRToolsInteractableSlider`s with a `KinematicFollower` body and a `SliderSwing`: the release speed carries the drawer on with friction, it bumps softly at the stops (`drawer_bump.wav`) and soft-closes within 3 cm. First use: the bedroom set (bed, wardrobe, nightstand with lamp), six artists in parallel.

## D-031: Fingertips press buttons; switches, alarms and hangers (2026-09-29)

The A/B panel's button didn't react in the headset: XR Tools' collision hand collides with its palm only (finger collision needs `hand_skeleton`), so a fingertip press never reached the button area. Each hand now carries a detection-only `Fingertip` Area3D (1.2 cm, Player Hands layer, on a BoneAttachment at the index tip): area buttons react to a poke, and nothing else changes, because full finger collision would also bump into handles and held objects. Built on that: `LightSwitch` (an area button toggling lights and an emissive material via `EmissiveMaterials`, shared with `HingeLight`) for the table lamps; `OpenAlarm` (the fridge beeps after 30 s open until it's closed); `HangingRail` and `RailHanger` (hangers are pickables with `release_mode = UNFROZEN`; dropped with the hook near a rail they hang there, shoulders across the rail). The Opus wardrobe got real sliding drawers, a pickable storage box with a lift-off lid, and six pickable hangers.

## D-032: Opus 5.5 is the default 3D artist; A/B testing ends (2026-09-29)

The bedroom-set A/B was blind and mixed per piece; the user picked every B: the bed (Opus), the wardrobe (Fable) and the nightstand (Opus). Across all five A/B pieces Opus won 3 (sofa, bed, nightstand) and Fable 2 (fridge, wardrobe), usually by a small margin; the user would have accepted every runner-up. Fable was faster (bedroom set 87 min and 606 k tokens against Opus's 119 min and 752 k; the Opus bed used Blender's cloth solver). Decision: `blender-artist` defaults to `opus`, and there are no more A/B tests unless the user asks. The runners-up stay as variants for other apartments, named by style: `sofa_boucle`, `bed_padded`, `wardrobe_lit`, `nightstand_square`. The apartment gets the winners under the plain names (`bed`, `wardrobe`, `nightstand`). The wardrobe winner got the other variant's interactivity (sliding drawers, storage box, hangers), and the bed got a collision surface that follows the duvet and pillows.

## D-033: Procedural windows from shared JSON specs (2026-09-30)

Windows are specs, not hand-built scenes: `tools/props/windows/*.json` holds each window's size, bays, sill, vent, shade, tint, LED, HUD and panel, plus one shared frame profile. The same file drives the Blender build (frame, sash and shade-bar glbs), the Godot scenes (`tools/props/window.py`: glass, collision, vent, shades, panel; placeholder boxes until the glbs exist, then the glbs automatically) and the apartment generator (it cuts the openings from the spec). Why: two agents build the two halves in parallel from one contract, and changing a window means editing numbers once. The living room became floor-to-ceiling (0..2.45 m), the kitchen sill rose to 0.9 m, and the bedroom got a tilt vent (10°, latch, city noise louder with the angle). Glass is one transparent layer per pane (style guide) in `window_glass.gdshader`: premultiplied alpha so reflections and the HUD aren't scaled down by the nearly clear coverage, low-frequency smudges only (no shimmer), smart-glass `tint` (clear, 0.5, 0.9: down to 4% transmission, a touch more reflective), a procedural 7-segment HUD (time, temperature, weather glyph; placeholder source until WorldState exists) and a reserved `rain_amount`, so rain drops with refraction slot in next. No screen texture yet. Tint and shade closure dim the room's city spill light (`WindowLight`), so the room really darkens; the room probes now reach past the window wall so the glass gets the room's reflection at full weight. Every window glb (frames, sash, shade bars, panel, button) embeds the same 1024² trim set; their import settings (written by `window.py --imports` before the first scan) map the `window_trim` material to one shared `assets/materials/window_trim.tres` and discard the embedded images, so there's one trim set in memory and no extracted copies per glb. Desktop perf with the real glbs: 298 draw calls (264 before), 209 k primitives (193 k), GPU p95 4.3 ms (5.2 ms before, within noise; the old glass boxes were two-sided and drew two layers), CPU p95 1.8 ms.

## D-034: Rain on the glass refracts through the screen texture, only while wet (2026-09-30)

Rain fills the glass shader's `rain()` hook, Heartfelt-style in the pane's meters (down = the pane's −Y, so the tilted vent carries its drops): a mist of micro-droplets (the blurred, haloed city), two layers of static beads (1.5–6 mm) that come and go while it rains, and runners that hang, grow, break loose and run down a wandering path, wiping a track through mist and beads and leaving tiny beads that dry out. The drops sit 12 mm outside the pane (per-eye parallax, so they read as outside in stereo). Each drop is a lens: it shows the view behind it through the screen texture, flipped and squeezed, with a dark rim and a small highlight. No shimmer: each layer fades by its drop size in pixels (fwidth) into the mist before its drops get sub-pixel, and the mist blur never drops below about 6 px (skyline test: 5.03 % dry, as before; 3.72 % with frozen full rain). `RainOnGlass` (`core/weather/`, `set_rain()` for the M2 weather) smooths intensity, wetness (drying over 45 s after the rain) and sliding (stops within 4 s), and drives the patter and the vent's outside rain. Why the screen texture: it's the only way the city appears in the drops; Godot 4.7 declares the Forward+ color buffer as a per-eye texture array under multiview, so it should work in stereo (confirm in the headset). Measured cost (desktop, interleaved medians): +0.69 ms GPU p95 at full rain, all of it the per-frame screen copy (the drop math is ~0.05 ms, mipmaps don't matter). Because a material that reads the screen makes Godot copy it every frame even when dry, the shader is split: `window_glass.gdshader` (dry, rain compiled out) and `window_glass_wet.gdshader`, swapped in only while the glass is wet (dry costs nothing: 5.00 ms against 5.02 ms for the old shader). The first swap stalled the main thread ~45 ms, so `RainOnGlass` draws the wet variant for three frames at startup. If stereo or the headset budget disagree, comment out `WINDOW_GLASS_RAIN_SCREEN` in the wet shader: drops then show a flat average (~+0.05 ms).

## D-035: Surfaces are tileable textures on the generated shell; doors bring their own frames (2026-10-01)

Floors, walls and ceilings stay the generator's boxes (D-015 keeps owning the layout) and get realism from tileable PBR sets instead of modeled rooms: flat walls gain nothing from geometry, and a Blender shell would freeze the layout. `blender/surfaces/` generates them deterministically with numpy (`arcology_blender.surface`: wrapping noise, normals, running bond) at 256–512 px/m: vinyl planks (7.32 m tile, a whole number of planks) in the living room, kitchen, hallway and vestibule, fitted carpet in the bedroom, polished concrete in the bathroom, painted plaster on every wall and a flatter plaster on the ceilings. The floor is split per room at the wall center lines, so the carpet edge sits under the bedroom door. The materials use `world_surface.gdshader`: world-space UVs along each face's own axis (BoxMesh faces are flat and axis-aligned), one sample per map instead of triplanar's three, and a correct tangent frame for the normal maps. Anisotropic filtering cost ~0.5 ms GPU on full-screen surfaces, so only the patterned floors (vinyl, concrete) use it; plaster and carpet use `world_surface_soft.gdshader` (plain mipmaps, the difference doesn't show on low-contrast surfaces). Doors are frame + leaf pairs from Blender (`door_interior`, `door_interior_bath` with a privacy thumb-turn inside, `door_entrance`: steel security door, smart-lock LED `door_entrance_lock_led`), each lining the 0.20 m reveal with casings on both faces, origin at the opening's bottom center on the wall plane, opening toward +Z; levers and thumb-turns are separate glbs on their axes so they can turn later. A future trim kit (skirting, ceiling details) won't need door casings. Desktop perf: GPU p95 4.85 ms (4.34 before), CPU p95 1.9 ms, 319 draw calls (298), 219 k primitives. Measure perf only while no Blender agent renders: Cycles on the same GPU inflated GPU p95 to ~5.8 ms.

## D-036: Skirting is swept in Blender along runs the apartment generator computes (2026-10-01)

The generator owns the layout, so it also knows where skirting goes: `tools/blockout/skirting.py` rasterizes the floor plan on the layout's 5 cm grid (floor boxes minus floor-standing walls, window openings and skipped rooms), traces the foot of the walls into loops and clips them at door frames (their glb bounds) and floor-level window openings. The result, `tools/blockout/apartment_skirting.json` (7 runs, 68.8 m, wrapping the archway reveals), is the contract for `blender/architecture/skirting/`, which sweeps one profile along it (`TrimMesh.polyline_sweep`: true miters, an eased outside arris, square ends) into one glb at world positions. The generator instances it under `Trim/Skirting` once it exists. A layout change means rerunning the generator and the Blender stages; `verify.py` checks coverage, ends and casings against the JSON. Profile: 80 x 9 mm painted MDF in the door frames' paint, so the casings (9.7 mm, entrance 12 mm) stand proud of it; board joints every 2.4 m come from the texture repeat. ## D-037: The player avatar is Silena Vesper on a humanoid skeleton with OpenXR hand joints (2026-10-03)

The XR Tools hands make way for the user's Shadowrun character (`docs/characters/silena_vesper.md`), built in stages: gloved hands, coat sleeves, the body seen when looking down, then head and hair. The base mesh comes from MPFB2 (Blender extension, GPLv3; its core assets and everything it generates are CC0; the CC-BY hair packs are avoided or credited). The Blender build renames and extends MPFB's rig accordingly. Grip and trigger poses are our own Blender actions driving `XRToolsHand`'s blend tree; the press `Fingertip` sits on the `IndexTip` bone; the XR Tools collision hand stays the physics hand and the avatar is visuals only. ## D-038: Avatar hands are fitted onto the XR Tools hand placement (2026-10-03)

Silena's gloved hands (stage 1 of D-037) replace the XR Tools hands without re-tuning where a hand sits on the controller: `tools/player/avatar_hands.gd` matches each glb's palm (center between wrist and middle knuckle, wrist-to-knuckle axis, index-to-little knuckle plane) to the XR Tools hand's in rest pose and keeps the glove's own size (wrist and knuckles land within 4 mm, the longer fingers reach 15 mm further), with a `TUNE` block for headset corrections. XR Tools keeps driving everything else: `AvatarHand` extends `XRToolsHand`, its palm offset moves an `Offset` node (it overwrites its first child's transform at runtime, so the fitted model sits one level down), and the generated blend tree blends the glb's `Open` and `Grip` per finger (trigger: index, grip: the rest). Without a `default_pose` the hand keeps those animations; XR Tools pose areas would swap in its own animations on the wrong bones, so per-object grab poses need avatar poses first. The XR Tools collision hand, Fingertip press areas (now on `<Side>IndexTip`) and grab behavior are unchanged. Cost: none measurable (interleaved desktop A/B GPU p95 5.39/5.10 ms old, 5.13/5.05 ms new; 358 draw calls both, +2.3 k primitives). The two glbs carry identical 2048² texture sets (left and right are mirrors with shared UVs); sharing one set is a later cleanup.

## D-039: Each avatar finger curls on the control it rests on (2026-10-03)

Holding the Steam Frame controller, the index finger rests on the bumper (shoulder), the middle finger on the trigger, ring and little fingers on the grip and the thumb on the stick or face buttons, so XR Tools' two-signal hand (trigger curls the index, grip the rest) looked wrong (headset feedback). New OpenXR actions `finger_index` (float), `finger_index_touch`/`_click`, `finger_middle` (float), `finger_middle_touch`, `finger_ring` (float, ring + little), `finger_thumb_touch`/`_click` are bound per controller (Frame as above; Touch and Index: index on the trigger, the other fingers on the grip, the thumb on stick, face buttons, thumb rest or trackpad); they only animate the hand, gameplay bindings are unchanged. `AvatarHand` reads them each physics frame (touch curls part way: 0.3, thumb 0.45; press or analog value up to a full grip), eases each finger at 14 curls/s and drives one Blend2 per finger group in the generated blend tree (Index, Middle, Ring, Thumb, each `Open` → `Grip` filtered to its bones). Controllers without `finger_*` bindings (all zero) fall back to XR Tools' trigger/grip mapping; `force_grip_trigger` keeps its meaning (trigger: index, grip: the rest). Godot 4.7.2 names the Frame's bumper `/input/bumper/*` (rejected paths are logged as "Unsupported io path" and their actions stay silent); Godot's development branch renames it to `/input/shoulder/*`, so check the action map after a Godot upgrade. The bumper's role as an index rest means binding gameplay to it later must keep the index curl meaningful.

## D-040: Avatar arms: full coat sleeves with headset-estimated shoulders (2026-10-03)

Stage 2 of D-037 shows the whole arm, not a forearm ending at the elbow: placing a forearm needs an elbow, an elbow needs a shoulder, and a sleeve cut off in midair at the elbow looks worse than a full arm whose top end sits at the edge of view. Each side is one glb (`silena_vesper_arm_<side>.glb`: glove + long leather coat sleeve, 13.2 k triangles, two 2048² material sets) on the bones `<Side>UpperArm` down to the finger tips plus `<Side>LowerArmTwist`, a deforming leaf child of LowerArm at mid-forearm. The hand scene's skeleton still rides the controller (D-038), so the hand bone is already in place; `ArmIK` (a GDScript `SkeletonModifier3D`, not Godot's `TwoBoneIK3D`, because the shoulder, the reach limit and the twist are game logic) puts the shoulder at a fixed offset from the eyes (the avatar's own: 17.9 cm out, 25.9 cm down, 10.4 cm back) in a body frame that follows the head's yaw lazily (35° dead zone), solves the elbow analytically in the plane of an elbow hint (down, back, slightly out), keeps each bone's rest frame relative to the arm line and the elbow's bend direction (so their roll follows the elbow, never the wrist), and gives 70 % of the hand's roll about the forearm to the twist bone, tracked continuously around -20° (no jump at half a turn). The first version aimed the bones and rolled them onto the hinge on whichever side was nearer: rolling the wrist past about -110° flipped upper arm and forearm half a turn (headset feedback, now the `arm_ik_*_roll` tests). When the arm lines up with the elbow hint (hanging down), the bend direction blends towards the body's back so it never degenerates. When the real hand is farther away than Silena's arm reaches, the shoulder slides toward it; the hand never leaves the controller. The shoulder end is a closed lining dome until stage 3 attaches the coat. Modifier results only exist during the skeleton update: tests read poses in `skeleton_updated`. Cost: interleaved desktop A/B GPU p95 5.56/5.12 ms with arms vs 5.18/5.01 ms with the XR Tools hands, +6 draw calls, +17 k primitives, CPU +0.1 ms.
